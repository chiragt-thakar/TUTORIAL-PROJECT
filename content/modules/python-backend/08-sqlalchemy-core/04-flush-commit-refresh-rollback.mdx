## Flush writes inside the transaction

`session.add()` makes an object pending. `flush()` emits pending SQL without ending the transaction. It obtains database-generated values and reveals constraint failures early. `commit()` flushes if needed, then commits the transaction.

```python
task = TaskModel(project_id=project_id, title="Ship API", status="open")
session.add(task)
session.flush()
assert task.id is not None
# more atomic work
session.commit()
```

Never call `commit()` merely to obtain an ID; flush is the correct boundary.

## Refresh, expire, and rollback

`refresh(task)` immediately re-reads mapped state from the database. Expiration marks attributes so later access reloads them; synchronous lazy reloads can hide I/O. `expire_on_commit=False` keeps loaded values usable after commit, commonly helpful in service code and async usage.

When flush fails, the database transaction is rolled back internally, but the session still requires an explicit `rollback()` before reuse.

```python
try:
    session.flush()
except IntegrityError as exc:
    session.rollback()
    raise DuplicateTaskError() from exc
```

Translate only recognized constraints. A generic `IntegrityError` could represent a programming defect or different invariant.

## Object states

Objects move through transient, pending, persistent, deleted, detached, and expired states. Closing a session detaches instances; accessing an unloaded relationship afterward fails. Return fully loaded domain/response data rather than relying on a closed session to fetch later.

<CommonMistake>

Catching an integrity error and continuing without rollback leaves the session in a failed transaction state. Every later statement fails until rollback.

</CommonMistake>

<ProductionNote>

Use constraints to arbitrate races, then translate a known constraint name to a domain conflict. “Check then insert” alone is not concurrency-safe.

</ProductionNote>

## Exercises

<Exercise id="sa-state-1" difficulty="easy">

Choose flush or commit when an audit row needs the new task's generated ID in the same atomic operation.

<Solution>

Flush the task, read its ID, add the audit row, then commit once at the operation boundary.

</Solution>
</Exercise>

<Exercise id="sa-state-2" difficulty="medium">

Why can `refresh()` be required after a database trigger changes a field?

<Solution>

The in-memory object may not know a trigger-computed value unless the dialect returns it. Refresh explicitly re-selects current database state.

</Solution>
</Exercise>

<Exercise id="sa-state-3" difficulty="hard">

Handle a duplicate project slug without masking other integrity failures.

<Solution>

Rollback, inspect the database-specific constraint identifier, translate only the named slug uniqueness constraint to `ProjectSlugConflict`, and re-raise unknown integrity failures.

</Solution>
</Exercise>

<Exercise id="sa-state-4" difficulty="interview">

Interview-style: "After `session.flush()` raises an `IntegrityError`, the database has already rolled back the failed transaction internally. Why does the session still require an explicit `rollback()` call before reuse?" Answer in three sentences or fewer.

<Solution>

The database rolling back only resolves the database's own state; the `Session` object separately maintains its own in-memory bookkeeping — pending objects, its own transactional tracking — that doesn't automatically reset just because the underlying database transaction ended. Until `session.rollback()` is explicitly called, the session considers itself in a failed state and refuses further operations.

The explicit call is what re-synchronizes the session's own state with the fact that the transaction underneath it is gone — it isn't a formality, it's required bookkeeping the database-side rollback can't do on the session's behalf.

</Solution>
</Exercise>

<Exercise id="sa-state-5" difficulty="real-world">

A route handler catches an `IntegrityError` from `session.flush()`, logs a warning, and returns a generic 400 — without calling `session.rollback()`. The next operation that reuses this same session raises a confusing, seemingly unrelated error on a completely different statement. Diagnose and fix using this lesson.

<Solution>

This is the common mistake this lesson names directly: catching the integrity error without rolling back leaves the session in a failed transaction state, so every subsequent statement on that same session raises until an explicit rollback happens — regardless of how unrelated that later statement looks to the original failure.

The confusing error is a symptom, not the real cause; the actual cause happened earlier and silently, at the moment the first `IntegrityError` was caught and swallowed without a rollback.

The fix is calling `session.rollback()` inside the `except` block before doing anything else with the session — exactly this lesson's own example, and non-negotiable regardless of whether the handler intends to re-raise, translate, or simply log the original error.

</Solution>
</Exercise>

<Gotchas>

<Gotcha question="Is it necessary to call `flush()` explicitly before `commit()` to ensure pending changes are actually sent?">

No — `commit()` flushes automatically if there are pending changes, so an explicit `flush()` isn't required just to make commit work. Explicit `flush()` is for when you need something *mid-transaction* — a database-generated ID, or to surface a constraint failure early — before the transaction actually ends.

</Gotcha>

<Gotcha question="Does an object's attribute automatically re-read from the database whenever the underlying row might have changed?">

No — without explicit expiration or a `refresh()` call, an already-loaded attribute keeps its in-memory value regardless of what changes elsewhere in the database. Expiration marks attributes so the *next access* triggers a reload; nothing reloads proactively on its own without that marking (or an explicit refresh) happening first.

</Gotcha>

<Gotcha question="Is catching and logging an `IntegrityError` enough to safely keep using the same session for other operations afterward?">

No — logging alone doesn't clear the session's failed transaction state. Every subsequent statement on that session will raise until `session.rollback()` is called explicitly, regardless of whether the original error was logged, swallowed, or re-raised.

</Gotcha>

</Gotchas>

## Summary

Flush synchronizes inside a transaction; commit makes it durable; refresh reloads; rollback restores session usability after failure. Translate database conflicts narrowly.
