## A session is one stateful work context

`Session` tracks ORM objects, pending changes, and one logical database transaction at a time. It is not thread-safe and must not be shared across concurrent requests.

```python
from sqlalchemy.orm import sessionmaker

SessionFactory = sessionmaker(bind=engine, expire_on_commit=False)

with SessionFactory.begin() as session:
    task = session.get(TaskModel, task_id)
    if task is None:
        raise TaskNotFoundError(str(task_id))
    task.status = "done"
```

The unit of work observes changes and flushes SQL in dependency order. The transaction boundary should surround one application operation, not one repository method.

## Identity map

Within a session, one database identity normally maps to one Python object. Repeated `get()` calls can return the identical instance without another query when present in the identity map.

```python
first = session.get(TaskModel, task_id)
second = session.get(TaskModel, task_id)
assert first is second
```

This is not a general query cache. Arbitrary selects still execute, and external database changes are not automatically merged into already-loaded objects. Expiration/refresh controls synchronization.

<TypeScriptComparison>

A Node query client often returns independent row objects per query. SQLAlchemy's session coordinates object identity and pending changes, so its lifetime materially changes behavior.

</TypeScriptComparison>

## Repository and unit of work

Repositories issue queries and stage mutations. A service or unit-of-work boundary decides commit/rollback so several repository calls remain atomic.

```python
with uow:
    project = uow.projects.require(project_id)
    task = Task.create(project, title)
    uow.tasks.add(task)
    uow.audit.add(AuditEvent.for_task(task))
    uow.commit()
```

<CommonMistake>

Do not store a session in a singleton repository. That shares identity and transaction state across requests and eventually produces stale data or concurrency failures.

</CommonMistake>

<ProductionNote>

Keep transactions short and free of remote network calls when possible. Waiting on another service while holding locks and a pooled connection reduces throughput and increases deadlock risk.

</ProductionNote>

## Exercises

<Exercise id="sa-session-1" difficulty="easy">

Why should “create task and audit event” use one session/transaction?

<Solution>

Both changes represent one business outcome. One transaction ensures either both persist or neither does; per-repository commits permit partial state.

</Solution>
</Exercise>

<Exercise id="sa-session-2" difficulty="medium">

Is the identity map proof that no second SELECT will run for any repeated query?

<Solution>

No. Primary-key `get` can reuse identity, but selects generally execute to determine matching rows. Existing identities are reused when rows are materialized.

</Solution>
</Exercise>

<Exercise id="sa-session-3" difficulty="hard">

Place an outbound email API call relative to the database transaction.

<Solution>

Persist an outbox event in the transaction, commit, then deliver asynchronously. Do not hold the transaction open across the remote call or risk a sent email with rolled-back state.

</Solution>
</Exercise>

<Exercise id="sa-session-4" difficulty="interview">

Interview-style: "Why can't a `Session` be shared across concurrent requests, even though a database connection pool is designed to be shared?" Answer in three sentences or fewer.

<Solution>

A `Session` is stateful — it tracks pending changes, an identity map, and one specific in-progress transaction — none of which are safe to touch from more than one request at once, and SQLAlchemy explicitly documents it as not thread-safe.

A connection pool, by contrast, is designed exactly for sharing: it hands out one connection per checkout and reclaims it afterward, with no cross-request state living inside the pool object itself.

The pool manages a shared *resource*; the session tracks request-specific *state*, and only one of those two things is safe to reuse concurrently.

</Solution>
</Exercise>

<Exercise id="sa-session-5" difficulty="real-world">

A singleton repository is implemented with `self.session = SessionFactory()` created once at application startup and reused for every request. After a few hours in production, unrelated requests start seeing each other's uncommitted or stale data, and the app eventually throws errors about a session already being in a failed transaction state. Diagnose using this lesson.

<Solution>

This is exactly the common mistake this lesson names: storing a session in a singleton shares identity-map state and transaction state across every request that touches it, since a session is stateful and not thread-safe.

One request's failed flush leaves the session unusable until an explicit rollback — and if other concurrent requests are mid-use of that same shared session when it happens, they inherit the failure too, alongside identity-map entries that may reflect data neither of them actually queried themselves.

The fix is creating a new session per request — function-scoped, constructed fresh inside a dependency on every call — never stored on a long-lived singleton that outlives any individual request.

</Solution>
</Exercise>

<Gotchas>

<Gotcha question="Is the identity map a general-purpose query cache?">

No — it only guarantees that repeated lookups of an *already-loaded* identity (typically via primary-key `get()`) return the same Python object without a new query. Arbitrary `select()` statements still execute against the database every time; the identity map reuses object identity for rows it already has, it doesn't cache query results generally.

</Gotcha>

<Gotcha question="Does `expire_on_commit=False` keep loaded attributes permanently synchronized with the database after commit?">

No — it only means attributes remain accessible without automatically triggering a reload immediately after commit. Those values can still go stale relative to the database over time; `refresh()` or expiration is still needed when current state genuinely matters.

</Gotcha>

<Gotcha question="Does calling `session.get(Model, id)` twice for the same identity guarantee zero SQL was ever executed for it?">

No — the *first* call still executes a query to load that row. Only the *second* and later calls for the same already-loaded identity reuse the identity map and skip an additional query; the identity map avoids repeat queries, not the original one.

</Gotcha>

</Gotchas>

<Checkpoint>

You can define the session's concurrency boundary, transaction boundary, identity behavior, and repository responsibility.

</Checkpoint>

## Summary

The session is a stateful unit of work with an identity map. Scope it to one sequential application operation and commit at the business boundary.
