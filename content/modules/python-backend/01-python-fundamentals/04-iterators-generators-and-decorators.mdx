## Iterable versus iterator

An iterable can produce an iterator through `iter(value)`. An iterator holds traversal state, returns itself from `__iter__`, and produces values from `__next__` until it raises `StopIteration`. Lists are reusable iterables; a generator object is a single-pass iterator.

```python
class TaskIds:
    def __init__(self, tasks: list[dict]) -> None:
        self._tasks = tasks

    def __iter__(self):
        for task in self._tasks:
            yield task["id"]
```

Most code should implement `__iter__` as a generator rather than hand-writing `__next__`. Consumers can loop without knowing how values are produced.

## Generators stream control

A function containing `yield` returns a generator immediately. Its body resumes on demand and suspends after each yield. This avoids creating a full result collection and supports pipelines.

```python
def batched_tasks(rows, size: int = 100):
    batch = []
    for row in rows:
        batch.append(row)
        if len(batch) == size:
            yield batch
            batch = []
    if batch:
        yield batch
```

Streaming is not magic: retaining references in `batch` still uses memory, and database drivers may buffer results. A generator can perform cleanup with `try/finally`, but a context manager makes ownership clearer when consumers might stop early.

<TypeScriptComparison>

Python generators resemble JavaScript generators, not promises. `yield` is pull-based iteration. `async def` plus `yield` creates an async generator consumed with `async for`; it does not make blocking work non-blocking.

</TypeScriptComparison>

## Decorators wrap definitions

`@decorator` is assignment syntax: `handler = decorator(handler)`. Framework route decorators register functions during import. Your decorators should preserve metadata and avoid hiding exceptions or signature meaning.

```python
from collections.abc import Callable
from functools import wraps
from time import perf_counter
from typing import ParamSpec, TypeVar

P = ParamSpec("P")
R = TypeVar("R")

def timed(fn: Callable[P, R]) -> Callable[P, R]:
    @wraps(fn)
    def wrapper(*args: P.args, **kwargs: P.kwargs) -> R:
        started = perf_counter()
        try:
            return fn(*args, **kwargs)
        finally:
            print(fn.__name__, perf_counter() - started)
    return wrapper
```

<CommonMistake>

Returning a list from a function that promises streaming defeats the memory benefit. Also remember that a generator's errors occur during iteration, not when the generator object is created.

</CommonMistake>

<ProductionNote>

Decorators are good for orthogonal behavior such as measurement. Authorization that needs request context is often clearer as a FastAPI dependency because the dependency graph remains inspectable.

</ProductionNote>

## Exercises

<Exercise id="py-iteration-1" difficulty="easy">

Write a generator `open_tasks(tasks)` that yields only tasks whose status is `open`, without creating an intermediate list.

<Solution>

```python
def open_tasks(tasks):
    for task in tasks:
        if task["status"] == "open":
            yield task
```

Each matching task is produced on demand.

</Solution>
</Exercise>

<Exercise id="py-iteration-2" difficulty="medium">

Why can a generator return no error at construction and then fail later? Demonstrate with an invalid row.

<Solution>

```python
def ids(rows):
    for row in rows:
        yield row["id"]

values = ids([{}])      # body has not run
next(values)            # KeyError happens here
```

Execution advances only when the consumer requests a value.

</Solution>
</Exercise>

<Exercise id="py-iteration-3" difficulty="hard">

Repair a decorator that returns `wrapper` but loses the wrapped function's name and documentation.

<Solution>

Apply `@functools.wraps(fn)` to `wrapper`. It copies metadata and exposes `__wrapped__`, which helps introspection and frameworks.

</Solution>
</Exercise>

<Exercise id="py-iteration-4" difficulty="interview">

Interview-style: "What's the practical difference between returning a list and returning a generator from a function that processes a large file?" Answer in three sentences or fewer.

<Solution>

Returning a list means the entire result is built and held in memory before the caller gets anything back, so peak memory scales with the size of the input.

Returning a generator means each item is produced only when the caller asks for the next one, so memory stays roughly constant regardless of input size — the tradeoff is that a generator can only be iterated once, while a list can be reused and indexed.

For a large file specifically, the generator version is usually the right default unless the caller genuinely needs random access or multiple passes.

</Solution>
</Exercise>

<Exercise id="py-iteration-5" difficulty="real-world">

A colleague wraps every service function with `@log_call`, but after adding it, FastAPI's automatic API docs stop showing the real parameter names for those endpoints — everything just shows up as `*args, **kwargs`. Using only what this lesson covered, name the bug and the fix.

<Solution>

The bug is a decorator that doesn't preserve the wrapped function's signature and metadata — without `@functools.wraps(fn)` on the inner `wrapper`, introspection tools (including the ones FastAPI uses to build its docs) see `wrapper`'s own generic `*args, **kwargs` signature instead of the original function's real one. The fix is adding `@wraps(fn)` to `wrapper` inside `log_call`, which restores the name, docstring, and enough metadata for introspection to work correctly again.

</Solution>
</Exercise>

<Gotchas>

<Gotcha question="If a generator function has a return statement, does it return that value to the caller like a normal function?">

Not the way you'd expect. `return value` inside a generator function doesn't hand `value` back from a call — it ends iteration and stores `value` on the `StopIteration` exception, retrievable via `.value` in advanced generator-delegation code, but invisible to a plain `for` loop entirely. If you need a return value from processing, a generator usually isn't the right tool.

</Gotcha>

<Gotcha question="Can you restart a generator by calling the generator function again with the same arguments?">

That creates a brand-new generator object, not a restart of the old one — the original generator, once exhausted, stays exhausted forever; there's no way to "rewind" it. If you need to iterate the same data twice, either call the generator function again or convert the results to a list once.

</Gotcha>

<Gotcha question="Do decorators run every time the decorated function is called?">

The decorator itself — the outer function — runs exactly once, at definition/import time, to produce the wrapped replacement. It's the inner `wrapper` function it returns that runs on every call. Mixing these two up is a common source of "why did my setup code only run once" confusion.

</Gotcha>

</Gotchas>

## Summary

Iteration protocols decouple production from consumption. Generators make lazy pipelines concise. Decorators transform callables at definition time, so preserve their metadata and keep behavior transparent.
