## Middleware wraps every request

Middleware is appropriate for request IDs, timing, security headers, and coarse logging. It should be cheap and should not contain resource-specific business rules.

```python
from time import perf_counter
from uuid import uuid4
from fastapi import Request

@app.middleware("http")
async def request_context(request: Request, call_next):
    request_id = request.headers.get("X-Request-Id") or str(uuid4())
    started = perf_counter()
    response = await call_next(request)
    response.headers["X-Request-Id"] = request_id
    logger.info("request_complete", extra={"request_id": request_id, "duration_ms": (perf_counter() - started) * 1000})
    return response
```

Use `try/finally` when timing must be logged on exceptions. Never log authorization headers or full request bodies by default.

## Exception translation

Application exceptions should remain protocol-neutral. Register handlers at the API boundary:

```python
@app.exception_handler(TaskNotFoundError)
async def task_not_found(request: Request, exc: TaskNotFoundError):
    return JSONResponse(status_code=404, content={"code": "task_not_found", "message": "Task not found"})
```

Return a stable machine code, safe message, and request ID. Log unexpected exceptions with stack traces; send clients a generic 500.

## Background tasks are small after-response work

FastAPI `BackgroundTasks` runs work after the response in the same application process. It suits small best-effort actions such as sending a non-critical notification through a reliable local client. It does not provide durability, retries, distributed coordination, or survival across process termination.

```python
@router.post("/{task_id}/complete")
async def complete(task_id: UUID, background: BackgroundTasks):
    task = service.complete(...)
    background.add_task(audit_sink.write, task.id, "completed")
    return task
```

<CommonMistake>

Do not put critical email, billing, large exports, or retryable integrations in in-process background tasks. Persist an outbox/job and let a worker own delivery.

</CommonMistake>

<ProductionNote>

Middleware ordering matters: the last added layer may wrap earlier layers. Test request IDs and security headers on both success and error responses.

</ProductionNote>

## Exercises

<Exercise id="api-middleware-1" difficulty="easy">

Ensure request duration is logged even when `call_next` raises.

<Solution>

Put the duration log in `finally`, store response-dependent values only when available, and re-raise the exception for the registered handler.

</Solution>
</Exercise>

<Exercise id="api-middleware-2" difficulty="medium">

Design a safe conflict error body for duplicate project membership.

<Solution>

Return 409 with fields such as a stable `code` (`"member_exists"`), a safe `message`, and a `request_id`. Do not include SQL or stack details.

</Solution>
</Exercise>

<Exercise id="api-middleware-3" difficulty="hard">

Request-ID middleware sets `response.headers["X-Request-Id"]` on the object returned by `call_next`. A registered exception handler translates a raised `TaskNotFoundError` into a 404 `JSONResponse` further down the stack. Trace whether the request ID header still ends up on that 404 response, and explain why.

<Solution>

Yes, it still ends up there. Exception handler resolution happens *inside* the framework's handling of the request — the exception is raised deep in the route, caught by the registered handler, and converted into a `JSONResponse` before that response object is ever handed back up to your middleware's `call_next` call.

By the time your middleware's line executes, `response` is already the handler's 404 `JSONResponse`, so setting a header on it works exactly the same as it would on a normal 200 response.

This is precisely why request-ID and timing middleware don't need special-case error handling of their own: as long as *something* eventually converts the exception into a `Response` before `call_next` returns, middleware wrapping it downstream sees a normal response object either way.

</Solution>
</Exercise>

<Exercise id="api-middleware-4" difficulty="interview">

Interview-style: "Why should resource-specific business rules stay out of middleware, even though middleware technically has access to the request?" Answer in three sentences or fewer.

<Solution>

Middleware runs unconditionally for every request that reaches the application, before routing has resolved which specific operation and typed dependencies apply — so resource-specific logic placed there either has to re-implement path matching itself or ends up applying rules to routes it was never meant to affect.

It also only has the raw request, not the validated, typed inputs a route's dependencies would already have resolved, so any resource-aware check has to redo work the framework is about to do properly anyway.

Middleware's value is being cheap and universal; the moment it needs to know which specific resource it's looking at, that logic belongs in a dependency or the route itself.

</Solution>
</Exercise>

<Exercise id="api-middleware-5" difficulty="real-world">

Classify thumbnail generation taking 30 seconds with required retries.

<Solution>

Use a durable queued job, not `BackgroundTasks`. Respond with 202 and a job/resource status when asynchronous completion is part of the API — an in-process background task offers no durability if the process restarts mid-generation, and no retry semantics if the generation step fails partway through.

</Solution>
</Exercise>

<Gotchas>

<Gotcha question="Does `BackgroundTasks` guarantee the task runs if the process crashes right after the response is sent?">

No — it runs in the same process, after the response, with no persistence layer behind it. If the process dies between sending the response and finishing the background task, that work is simply lost, which is exactly why it's only appropriate for small, non-critical, best-effort actions.

</Gotcha>

<Gotcha question="Does middleware only run for the specific routes it seems relevant to?">

No — unless explicitly scoped, middleware wraps every request the application receives, regardless of which route eventually matches. That's what makes it suitable for universal concerns like timing and request IDs, and unsuitable for anything that only makes sense for one resource type.

</Gotcha>

<Gotcha question="If an exception is caught by a registered exception handler, does code in middleware that runs after `call_next` still execute normally?">

Yes — the exception handler converts the exception into a normal `Response` object before `call_next` returns control to the middleware, so any middleware code that runs afterward (adding headers, logging timing) sees a standard response and behaves exactly as it would for a non-error request.

</Gotcha>

</Gotchas>

<Checkpoint>

You can place cross-cutting transport work in middleware, map application failures in handlers, and reject background work that needs durability.

</Checkpoint>

## Summary

Middleware wraps transport concerns, exception handlers stabilize public failures, and in-process background tasks are only for short non-critical work.
