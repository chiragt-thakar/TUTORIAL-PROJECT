## Async is cooperative waiting

Calling an `async def` function creates a coroutine; `await` lets that coroutine pause while an awaitable completes. The event loop can then run other tasks. It cannot preempt arbitrary Python code.

```python
@router.get("/{task_id}")
async def get_task(task_id: UUID, service: AsyncTaskServiceDep) -> TaskRead:
    task = await service.get(TaskId(str(task_id)))
    return TaskRead.model_validate(task, from_attributes=True)
```

Use `async def` when the libraries you call expose awaitable I/O. A synchronous path operation declared with `def` is run by FastAPI in a thread pool. But a blocking function called directly inside your own `async def` runs on the event-loop thread and blocks other requests.

## Choose from the deepest I/O boundary

- Async database/HTTP client: use `async def` and `await` through the call chain.
- Synchronous blocking library: use a normal `def` operation or explicitly run the blocking call in a worker thread.
- CPU-heavy work: use a process/job system; threads do not make Python CPU work scale predictably.

```python
from anyio import to_thread

result = await to_thread.run_sync(blocking_pdf_parser, payload)
```

Do not add `async` to pure functions. Call them normally from async code. `await` is only for awaitables.

<TypeScriptComparison>

JavaScript promises and Python coroutines both enable cooperative I/O, but Python `async def` does not execute until awaited or scheduled. A blocking Python library remains blocking even inside an async function.

</TypeScriptComparison>

<CommonMistake>

`async def endpoint(): time.sleep(2)` freezes the event loop thread. Use `await asyncio.sleep(2)` for an async wait or isolate a genuinely blocking library.

</CommonMistake>

<ProductionNote>

Concurrency amplifies downstream pressure. Bound fan-out, configure client and pool limits, use timeouts, and avoid launching unbounded `gather()` calls from user-controlled input.

</ProductionNote>

## Exercises

<Exercise id="api-async-1" difficulty="easy">

Classify `requests.get`, `httpx.AsyncClient.get`, and password hashing inside an async endpoint.

<Solution>

`requests.get` is blocking and must be replaced or moved to a thread. `AsyncClient.get` is awaited. Password hashing is CPU-expensive blocking work and should run in a bounded worker thread/process according to the hashing library and load profile.

</Solution>
</Exercise>

<Exercise id="api-async-2" difficulty="medium">

Why does merely changing `def repository_call` to `async def` not make a synchronous driver non-blocking?

<Solution>

The driver still performs blocking I/O on the calling thread. Async behavior requires an awaitable driver or explicit isolation.

</Solution>
</Exercise>

<Exercise id="api-async-3" difficulty="hard">

A teammate moves a CPU-bound image-resizing function into `await anyio.to_thread.run_sync(resize_image, payload)`, expecting better throughput under load. Latency per request improves slightly, but overall throughput barely changes and CPU usage pegs at 100% well before the thread pool's configured limit is reached. Diagnose why moving CPU-bound work to a thread doesn't scale the way moving blocking I/O to a thread does.

<Solution>

Threads free the event loop from *waiting* on I/O, but Python's GIL means only one thread executes Python bytecode at a time regardless of how many threads exist. A CPU-bound function holds the GIL for its entire duration, so running it in a worker thread doesn't add real parallelism — it just relocates where the blocking happens while everything still serializes at the GIL.

This is exactly why this lesson's I/O-boundary guidance puts CPU-heavy work in its own bucket (a process/job system) rather than "isolate it in a thread": threads solve blocking-on-I/O, not blocking-on-computation.

</Solution>
</Exercise>

<Exercise id="api-async-4" difficulty="interview">

Interview-style: "Why can't the event loop preempt a long-running synchronous function the way an OS scheduler preempts a thread?" Answer in three sentences or fewer.

<Solution>

`asyncio`'s event loop runs cooperative, single-threaded multitasking — a coroutine only hands control back to the loop at an `await` point it chooses to hit, not at some externally imposed interval. There's no timer interrupt forcibly suspending running Python bytecode mid-execution the way an OS scheduler preempts a thread. So a function with no `await` inside it, however long it runs, monopolizes the loop for that entire duration once started.

</Solution>
</Exercise>

<Exercise id="api-async-5" difficulty="real-world">

One user request triggers `asyncio.gather(*[fetch(id) for id in user_supplied_ids])`, where `user_supplied_ids` can contain thousands of entries. A downstream service becomes overwhelmed and starts timing out for every tenant, not just this one. Using only what this lesson covered, diagnose and fix it.

<Solution>

`gather()` launches every coroutine concurrently with no built-in limit, so a large enough user-supplied list turns one request into thousands of simultaneous downstream calls — exactly the unbounded fan-out from user-controlled input this lesson's production note warns against. Because the downstream service is shared, the damage isn't contained to the triggering user's request; every other tenant relying on that same downstream dependency degrades too.

The fix is bounding concurrency explicitly — a semaphore, fixed-size batches, or a worker pool — so the number of simultaneous downstream calls has a hard ceiling regardless of input size, plus a timeout per call so one slow downstream response can't hold a concurrency slot indefinitely.

</Solution>
</Exercise>

<Gotchas>

<Gotcha question="Does declaring a function `async def` automatically make its body non-blocking?">

No — `async def` only makes a function awaitable; it does nothing to the blocking behavior of whatever code runs inside it. A blocking library call inside an `async def` function still blocks the event-loop thread exactly as it would in a synchronous function, unless it's genuinely awaitable I/O.

</Gotcha>

<Gotcha question="Does moving CPU-bound work into a worker thread give it real parallelism in Python?">

No — the GIL means only one thread executes Python bytecode at a time, so a CPU-bound function in a thread still serializes with every other thread doing Python work. Threads are the right tool for blocking I/O, where the thread spends most of its time waiting rather than computing — not for CPU-heavy work, which needs a separate process to actually run in parallel.

</Gotcha>

<Gotcha question="Can `asyncio.gather()` be trusted to run a list of coroutines at a safe, bounded concurrency automatically?">

No — `gather()` has no concept of a concurrency limit; it schedules every coroutine you pass it at once. If the size of that list is influenced by user input, an explicit bound (a semaphore or batching) is required, or the fan-out scales directly with whatever the caller sends.

</Gotcha>

</Gotchas>

<Checkpoint>

You can inspect every I/O call on a route and state whether it awaits, uses FastAPI's thread pool, blocks the loop, or belongs in a job worker.

</Checkpoint>

## Summary

Async improves concurrency only when waiting is cooperative. Match the endpoint to its libraries, isolate blocking calls deliberately, and treat CPU-heavy or unbounded work as a separate capacity problem.
