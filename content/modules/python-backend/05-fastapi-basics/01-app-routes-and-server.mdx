## The ASGI application

`FastAPI()` creates an ASGI callable. An ASGI server such as Uvicorn owns sockets, concurrency, and process lifecycle; FastAPI owns routing, dependency resolution, validation, and response generation.

```python title="src/task_api/main.py"
from fastapi import FastAPI

app = FastAPI(title="Task API", version="1.0.0")

@app.get("/health")
async def health() -> dict[str, str]:
    return {"status": "ok"}
```

```bash
uv run fastapi dev src/task_api/main.py
# or: uv run uvicorn task_api.main:app --reload
```

The import string means “import `task_api.main`, then retrieve `app`.” The development reloader starts extra process machinery and must not be used in production.

## Route registration

`@app.get(...)` executes at import time and registers the decorated callable plus metadata. The path and method identify an operation. Static routes should be registered before overlapping dynamic routes when ambiguity is possible.

```python
@app.get("/tasks/me")
async def my_tasks() -> list[dict]:
    ...

@app.get("/tasks/{task_id}")
async def get_task(task_id: str) -> dict:
    ...
```

Returning a dictionary or Pydantic model lets FastAPI build a response. This convenience does not remove the need to choose a response schema and status code.

<TypeScriptComparison>

The ASGI server/FastAPI split resembles Node's HTTP runtime plus Express router, but Python module import performs decorator registration. The callable type and generated OpenAPI are derived from runtime annotations.

</TypeScriptComparison>

<CommonMistake>

Do not start Uvicorn at module import. Export `app`; let the command or process manager start it. This keeps tests, migrations, and tooling import-safe.

</CommonMistake>

<ProductionNote>

Use an application factory only when environments or tests truly require multiple differently configured app instances. A simple exported app with explicit lifespan and wiring is easier until then.

</ProductionNote>

## Exercises

<Exercise id="api-app-routes-1" difficulty="easy">

Add `GET /` returning the service name and semantic version.

<Solution>

```python
@app.get("/")
async def root() -> dict[str, str]:
    return {"name": "task-api", "version": "1.0.0"}
```

</Solution>
</Exercise>

<Exercise id="api-app-routes-2" difficulty="medium">

Routes are registered in this order: `/tasks/{task_id}` first, then `/tasks/me`. Predict what happens when a client requests `GET /tasks/me`, then fix it.

<Solution>

FastAPI matches routes in registration order, so `GET /tasks/me` matches `/tasks/{task_id}` first, with `task_id` bound to the literal string `"me"` — the dedicated `/tasks/me` handler never runs. The fix is to register the static route before the overlapping dynamic one, not to change either handler's body.

</Solution>
</Exercise>

<Exercise id="api-app-routes-3" difficulty="hard">

Explain why `uvicorn src.task_api.main:app` is usually wrong for an installed src-layout package (the layout Module 3 set up), and give the correct import string.

<Solution>

`src` is a source directory used to force explicit installs — it is not part of the installed package's import name. Once the project is installed, the importable path is `task_api.main:app`; prefixing it with `src.` looks for a top-level package called `src` that doesn't exist as an installed module.

</Solution>
</Exercise>

<Exercise id="api-app-routes-4" difficulty="interview">

Interview-style: "When exactly does `@app.get(...)` run, and why does that matter for testing?" Answer in three sentences or fewer.

<Solution>

The decorator runs at import time — when Python executes the module that defines the route, not when a request arrives — and it registers the callable plus its metadata on the app.

That means importing `task_api.main` for any reason, including test collection or a tooling script, re-runs every decorator in that module. Any side effect placed at module level, not just inside a route body, therefore fires during import — which is exactly why import-time code must stay safe to run repeatedly and without a network call.

</Solution>
</Exercise>

<Exercise id="api-app-routes-5" difficulty="real-world">

A teammate adds `uvicorn.run(app)` at the top level of `main.py` so `python main.py` starts the server conveniently. CI now hangs during test collection instead of failing. Diagnose and repair the boundary.

<Solution>

`pytest` imports `main.py` to discover fixtures and routes reachable from it, and importing the module executes every top-level statement — including `uvicorn.run(app)`, which blocks forever serving requests, so collection never returns and CI hangs instead of producing a clean failure.

Remove the top-level call entirely; start the server through the `fastapi dev` or `uvicorn` CLI instead. If a script entry point is genuinely required, guard it with `if __name__ == "__main__":` so the call only executes when the file is run directly, never on import.

</Solution>
</Exercise>

<Gotchas>

<Gotcha question="Does creating `app = FastAPI()` start the server?">

No — it constructs an ASGI callable and nothing more. Nothing listens on a socket until a separate ASGI server, such as Uvicorn, is pointed at that callable and started.

</Gotcha>

<Gotcha question="Does FastAPI pick the most specific matching route automatically, regardless of registration order?">

No — routing is first-match by registration order, not by specificity. A dynamic path registered before a static one that could also match will shadow it, so overlapping static routes must be declared first.

</Gotcha>

<Gotcha question="Is `--reload` safe to leave on in production?">

No — the reloader watches the filesystem and manages extra worker processes purely to speed up local iteration. That overhead and process model are dev-only; production runs a fixed set of worker processes with reload disabled.

</Gotcha>

</Gotchas>
