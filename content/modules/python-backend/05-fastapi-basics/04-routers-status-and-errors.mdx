## Routers organize one API

`APIRouter` groups related operations, shared prefixes, tags, dependencies, and response metadata. It is not a separate application.

```python title="src/task_api/api/routers/tasks.py"
from fastapi import APIRouter

router = APIRouter(prefix="/tasks", tags=["tasks"])

@router.get("/{task_id}", response_model=TaskRead)
async def get_task(task_id: UUID) -> TaskRead:
    ...
```

```python title="src/task_api/main.py"
from task_api.api.routers import tasks

app.include_router(tasks.router, prefix="/api/v1")
```

Group by domain capability rather than one file per HTTP verb. Keep business decisions in services so routers remain adapters.

## Status codes communicate outcomes

Start with this small status-code map:

- `200 OK`: a successful read or update that returns a body.
- `201 Created`: a new resource was created.
- `204 No Content`: the action succeeded and there is no response body.
- `401 Unauthorized`: credentials are missing or invalid.
- `403 Forbidden`: identity is known, but the action is not allowed.
- `404 Not Found`: the resource is unavailable to this caller.
- `409 Conflict`: the request clashes with current state, such as duplicate membership.

Use `400 Bad Request` for request problems that do not fit your normal validation response. The exact choice matters less than using one documented rule consistently.

Raise `HTTPException` in the API layer for simple HTTP failures:

```python
from fastapi import HTTPException

try:
    task = service.require(TaskId(str(task_id)))
except TaskNotFoundError as exc:
    raise HTTPException(status_code=404, detail="Task not found") from exc
```

Larger applications should translate domain exceptions centrally so repeated routes do not drift.

<TypeScriptComparison>

An Express router provides similar grouping, but FastAPI composes router metadata into one OpenAPI document and runs typed dependencies declared on routers and operations.

</TypeScriptComparison>

<CommonMistake>

Do not return `{"error": ...}` with HTTP 200. Monitoring, clients, caches, and retry policies interpret the status code independently of the JSON body.

</CommonMistake>

<ProductionNote>

Returning 404 instead of 403 can hide resource existence from unauthorized users. Make that an explicit security policy and test it consistently.

</ProductionNote>

## Exercises

<Exercise id="api-routers-1" difficulty="easy">

Create a projects router mounted at `/api/v1/projects` and tagged `projects`.

<Solution>

Define `APIRouter(prefix="/projects", tags=["projects"])`, then include it with `app.include_router(router, prefix="/api/v1")`.

</Solution>
</Exercise>

<Exercise id="api-routers-2" difficulty="medium">

Choose the status for attempting to add an already-existing project member.

<Solution>

409 Conflict communicates that the request conflicts with current resource state. Document the stable error code in the response body as well.

</Solution>
</Exercise>

<Exercise id="api-routers-3" difficulty="hard">

Every route on the projects router must require an authenticated actor. Declare that once at the router level instead of repeating a dependency on every route function.

<Solution>

```python
router = APIRouter(
    prefix="/projects",
    tags=["projects"],
    dependencies=[Depends(require_actor)],
)
```

`APIRouter` accepts a `dependencies` list that applies to every route included on that router, the same way `prefix` and `tags` apply router-wide. Individual routes can still add further dependencies of their own; they inherit this one without restating it.

</Solution>
</Exercise>

<Exercise id="api-routers-4" difficulty="interview">

Interview-style: "A caller is authenticated but not authorized to view a specific project. Should the endpoint return 404 or 403?" Answer in three sentences or fewer.

<Solution>

Both are defensible, but they express different security policies, not different bugs — 403 confirms the resource exists and access was denied, while 404 hides its existence entirely from unauthorized callers. Which one is correct depends on whether resource existence itself is sensitive information for that domain (a private repository's existence, for example, is often treated as sensitive).

Whichever choice is made, it needs to be a deliberate, consistently-applied policy rather than whatever a given route happens to raise.

</Solution>
</Exercise>

<Exercise id="api-routers-5" difficulty="real-world">

Three separate route functions each catch `TaskNotFoundError` and raise their own `HTTPException(404, ...)`, and a fourth route added last sprint forgot to — it leaks a raw 500 instead. Fix the duplication and the gap in one change.

<Solution>

Define one application-level exception handler that maps `TaskNotFoundError` to a consistent 404 payload, and register it once with `app.add_exception_handler` (or `@app.exception_handler`). Remove the per-route `try`/`except`/`raise HTTPException` blocks entirely — routes call the service and let the exception propagate.

This closes today's gap and every future one: a new route that forgets to handle the exception now gets the correct 404 automatically instead of a raw 500, because the translation lives in exactly one place instead of being copy-pasted per route.

</Solution>
</Exercise>

<Gotchas>

<Gotcha question="Is an `APIRouter` a separate mini-application with its own middleware and lifespan?">

No — it's purely an organizational and metadata-grouping tool. Prefix, tags, dependencies, and response metadata declared on a router get merged into the one application it's included into; there's no separate app boundary, request pipeline, or lifespan to reason about.

</Gotcha>

<Gotcha question="Does returning HTTP 200 with an error-shaped JSON body communicate failure correctly?">

No — monitoring systems, HTTP clients, caches, and retry policies all key off the status code, independent of body contents. A 200 status tells every layer below your application code that the request succeeded, regardless of what the JSON says.

</Gotcha>

<Gotcha question="Does raising the same domain exception from two different routes guarantee they produce the same HTTP response?">

Only if the translation is centralized. If each route independently catches the exception and builds its own `HTTPException`, they will drift — different status codes, different detail strings — the moment one route gets updated and the others don't. A single registered exception handler is what guarantees consistency.

</Gotcha>

</Gotchas>

<Checkpoint>

You can place an operation in the correct router and select a status based on HTTP semantics rather than convenience.

</Checkpoint>

## Summary

Routers modularize one application; services own business behavior; status codes express protocol outcomes; and centralized exception translation prevents inconsistent APIs.
