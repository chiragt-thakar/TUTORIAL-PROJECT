## Authentication proves an identity

OAuth2 defines authorization flows; it is not a token format. For a first-party API, a login endpoint may verify credentials and issue a short-lived bearer access token. OpenID Connect is the identity layer used when delegating login to an identity provider.

FastAPI's `OAuth2PasswordBearer` extracts a bearer token and describes the security scheme. It does not verify signatures or users.

```python
oauth2_scheme = OAuth2PasswordBearer(tokenUrl="/api/v1/auth/token")

async def get_current_user(token: Annotated[str, Depends(oauth2_scheme)]) -> User:
    claims = token_service.decode_and_verify(token)
    return await user_service.require_active(UserId(claims.subject))
```

## Passwords and tokens

Store salted, adaptive password hashes using a maintained library and a memory-hard algorithm such as Argon2 where operationally suitable. Never encrypt passwords for later recovery. Verify with the library's constant-time-compatible API and support rehashing when parameters change.

A JWT is a signed set of claims, not encrypted by default. Validate allowed algorithm, signature, issuer, audience, expiration, not-before where used, and required claims. Use short access-token lifetimes. Refresh tokens need rotation/revocation policy and secure storage; a stateless access JWT does not solve logout by itself.

```python
class AccessClaims(NamedTuple):
    subject: str
    expires_at: datetime
    token_id: str
```

Keep key material in secret management. Do not accept the token's `alg` choice without an allowlist. Include minimal claims; roles and permissions can become stale before expiry.

<TypeScriptComparison>

The same JOSE and password-hashing rules apply in Node. Python's dependency system makes extraction and identity resolution composable, but the framework does not choose a secure key lifecycle for you.

</TypeScriptComparison>

<CommonMistake>

Do not place secrets, password hashes, or sensitive profile data inside a JWT. Signed payloads are readable by the holder.

</CommonMistake>

<ProductionNote>

Rate-limit authentication attempts, return generic credential failures, log token IDs rather than raw tokens, rotate signing keys deliberately, and synchronize clocks.

</ProductionNote>

## Exercises

<Exercise id="security-oauth-1" difficulty="easy">

Why is SHA-256 alone inappropriate for stored passwords?

<Solution>

It is intentionally fast, enabling massive guessing. Password hashing needs a unique salt and expensive adaptive work factor through a purpose-built algorithm/library.

</Solution>
</Exercise>

<Exercise id="security-oauth-2" difficulty="medium">

List the minimum checks for accepting an access JWT.

<Solution>

Verify signature with an allowed algorithm/key, issuer, audience, expiration, required subject, and any not-before constraint. Then load or validate the current active identity and authorization state.

</Solution>
</Exercise>

<Exercise id="security-oauth-3" difficulty="hard">

Design logout for short-lived access tokens plus refresh tokens.

<Solution>

Revoke/rotate the refresh token server-side, clear its secure cookie/storage, and let the short-lived access token expire; use a denylist only when immediate access-token revocation is required and worth the state cost.

</Solution>
</Exercise>

<Exercise id="security-oauth-4" difficulty="interview">

Interview-style: "Are OAuth2 and JWT the same thing? If not, what does each one actually define?" Answer in three sentences or fewer.

<Solution>

No — OAuth2 is an authorization framework defining *flows* for how a client obtains an access token (grant types, redirect handling, roles), and it says nothing about what that token itself looks like. JWT is one specific *token format* — a signed set of claims — commonly used to carry the token an OAuth2 flow produces, but OAuth2 doesn't require JWTs and JWTs show up plenty outside OAuth2 entirely.

Conflating the two tends to mean skipping OAuth2 flow security (redirect URI validation, state parameter) because "it's just a JWT," or skipping JWT verification rigor because "OAuth2 handles security" — neither one covers what the other actually guarantees.

</Solution>
</Exercise>

<Exercise id="security-oauth-5" difficulty="real-world">

A security audit finds your JWT verification code reads the `alg` header from the incoming token itself to decide which verification method to run — so a token claiming `alg: none` skips signature verification entirely, and a token claiming `alg: HS256` gets checked against your RS256 public key treated as an HMAC secret (which is derivable from a public key). Using only what this lesson covered, name the fix.

<Solution>

Never treat the algorithm named in the token's own header as authoritative — verify against an explicit server-side allowlist of accepted algorithms, with the verification key selected by your own configuration for the expected algorithm, independent of whatever the token claims about itself.

This closes both attacks: `alg: none` is never in the allowlist, so it's rejected outright, and algorithm-confusion (treating an RSA public key as an HMAC secret) is prevented because the key-to-algorithm mapping is fixed by your configuration, not by an attacker-controlled header field.

</Solution>
</Exercise>

<Gotchas>

<Gotcha question="Does a valid JWT signature guarantee the claims inside are still trustworthy for the token's entire stated lifetime?">

No — a valid signature only proves the claims haven't been tampered with since signing, not that they're still current. Roles and permissions embedded in a token can become stale before the token expires (a user's access is revoked mid-lifetime, for instance), which is exactly why minimal claims and short lifetimes both matter.

</Gotcha>

<Gotcha question="Is encrypting stored passwords with a reversible cipher an acceptable alternative to hashing them?">

No — reversible encryption means anyone with the key (an attacker who breaches the server, a rogue insider) can recover every plaintext password at once. Passwords need a one-way, adaptive hash specifically so recovery is never possible for anyone, including you.

</Gotcha>

<Gotcha question="Does a JWT provide confidentiality for the data in its claims, the way encryption would?">

No — a JWT is signed, not encrypted, by default. Its claims are base64-encoded and trivially readable by anyone who holds the token, which is exactly why secrets and sensitive profile data must never be placed inside one.

</Gotcha>

</Gotchas>

<Checkpoint>

You can separate credential verification, OAuth2 flow, bearer extraction, JWT verification, current-user loading, and authorization.

</Checkpoint>

## Summary

OAuth2 organizes token acquisition; JWT is one signed token format; password hashing is a separate adaptive primitive. Validate every trust claim and keep access tokens short-lived.
