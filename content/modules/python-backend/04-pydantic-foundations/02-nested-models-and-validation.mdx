## Validation follows the object graph

Nested Pydantic models validate recursively and produce precise error locations. Model reusable value shapes instead of leaving inner dictionaries untyped.

```python
from pydantic import BaseModel, Field

class AssigneeInput(BaseModel):
    user_id: str
    display_name: str = Field(min_length=1)

class TaskCreate(BaseModel):
    title: str
    assignees: list[AssigneeInput] = Field(default_factory=list)
```

Use `default_factory` for lists, dictionaries, timestamps, and generated IDs. It runs per model instance and states intent even though Pydantic protects many mutable defaults.

## Field and model validators

A field validator normalizes or validates one field. A model validator handles relationships between fields. Prefer built-in constraints first because they produce standard schema and errors.

```python
from datetime import datetime
from typing import Self
from pydantic import BaseModel, field_validator, model_validator

class TaskWindow(BaseModel):
    title: str
    starts_at: datetime | None = None
    due_at: datetime | None = None

    @field_validator("title")
    @classmethod
    def normalize_title(cls, value: str) -> str:
        value = value.strip()
        if not value:
            raise ValueError("title cannot be blank")
        return value

    @model_validator(mode="after")
    def due_after_start(self) -> Self:
        if self.starts_at and self.due_at and self.due_at < self.starts_at:
            raise ValueError("due_at must not precede starts_at")
        return self
```

Before validators see raw input and are easy to overuse. After validators operate on typed fields and are usually safer for cross-field rules. Validators should be deterministic: no database calls, HTTP calls, or current-user authorization.

<TypeScriptComparison>

Nested TypeScript interfaces preserve static shapes only. Pydantic recursively constructs nested runtime models and reports locations such as `assignees.2.user_id`, similar to a schema-validation library.

</TypeScriptComparison>

<CommonMistake>

Do not check whether an assignee exists in the database inside a model validator. That couples parsing to I/O, complicates async execution, and turns validation errors into stale authorization decisions. Put it in the service layer.

</CommonMistake>

<ProductionNote>

Normalize only when the contract promises normalization. Lowercasing an email may be appropriate; lowercasing a case-sensitive external identifier silently corrupts data.

</ProductionNote>

## Exercises

<Exercise id="pydantic-nested-1" difficulty="easy">

Model a task with a list of labels where every label has a non-empty `name` and optional six-digit hex `color`.

<Solution>

```python
class LabelInput(BaseModel):
    name: str = Field(min_length=1)
    color: str | None = Field(default=None, pattern=r"^#[0-9a-fA-F]{6}$")

class TaskInput(BaseModel):
    labels: list[LabelInput] = Field(default_factory=list)
```

</Solution>
</Exercise>

<Exercise id="pydantic-nested-2" difficulty="medium">

Reject a task whose `completed_at` is set while status is not `done`.

<Solution>

Use an after model validator, compare the typed fields, raise `ValueError` on the invalid combination, and return `self` otherwise.

</Solution>
</Exercise>

<Exercise id="pydantic-nested-3" difficulty="hard">

Why is `assignees: list[dict[str, object]]` weaker than a nested model?

<Solution>

It validates only that each item is a dictionary. It does not require named keys, construct typed values, produce a useful JSON Schema, or give precise inner-field errors.

</Solution>
</Exercise>

<Exercise id="pydantic-nested-4" difficulty="interview">

Interview-style: "What's the difference between a `field_validator` and a `model_validator`, and when would you reach for each?" Answer in three sentences or fewer.

<Solution>

A `field_validator` normalizes or checks one field in isolation and can't see any other field's value. A `model_validator` (typically `mode="after"`) runs once every field has been individually validated and can compare fields against each other — the only place a cross-field rule like "due date can't precede start date" can correctly live. Use built-in constraints first, `field_validator` for single-field normalization, and `model_validator` specifically for relationships between fields.

</Solution>
</Exercise>

<Exercise id="pydantic-nested-5" difficulty="real-world">

A teammate adds a `field_validator` on `title` that queries the database to reject duplicate task titles, reasoning "validators are the natural place to enforce rules." Using only what this lesson covered, explain what's wrong with this design.

<Solution>

Validators are expected to be deterministic and side-effect-free — no database calls, no HTTP calls, no dependence on a current-user session. A DB-querying validator couples parsing to I/O, makes the model unusable outside an async/request context, makes unit-testing the model require a real or mocked database, and turns a validation error into what's actually a stale business-rule check (the title could become non-unique moments later from a concurrent write anyway).

Duplicate-title uniqueness is a service-layer concern enforced against the database at the point of the actual write, not a parsing-time concern.

</Solution>
</Exercise>

<Gotchas>

<Gotcha question="If a field validator raises an error for one field, does the model's after-validator still run?">

No — an after-validator needs a fully constructed, individually-validated instance to run against (it receives `self`). If any field fails its own validation, Pydantic reports that field's error and never reaches the after-validator at all.

</Gotcha>

<Gotcha question="Is `default_factory` only useful for mutable defaults like lists and dicts?">

No — it's for anything that must be computed fresh per instance, which includes mutable containers but also things like a generated timestamp (`datetime.utcnow`) or a generated ID. The common thread is "evaluated once per instance," not "happens to be mutable."

</Gotcha>

<Gotcha question="Can a field validator see another field's already-validated value to cross-check against it?">

No — a `field_validator` only ever sees the one field it's attached to. Cross-field logic needs an after `model_validator`, which is exactly why this lesson draws that line so deliberately: reaching for a field validator to enforce a relationship between two fields simply won't work.

</Gotcha>

</Gotchas>

<Checkpoint>

You can decide whether an invariant belongs to a built-in constraint, field validator, model validator, or service operation.

</Checkpoint>

## Summary

Nested models make object graphs explicit. Use factories for per-instance defaults, standard constraints for simple rules, and after-model validators for deterministic relationships between typed fields.
