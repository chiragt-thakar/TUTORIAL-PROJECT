## Runtime boundary, not domain magic

Pydantic reads untrusted Python values, applies a declared schema, and returns a model whose fields satisfy that schema. It is most valuable where data crosses a boundary: HTTP, environment variables, messages, or loosely typed libraries.

```python title="src/task_api/schemas/tasks.py"
from datetime import datetime
from uuid import UUID
from pydantic import BaseModel, ConfigDict, Field

class TaskCreate(BaseModel):
    model_config = ConfigDict(extra="forbid")

    title: str = Field(min_length=1, max_length=120)
    project_id: UUID
    priority: int = Field(default=2, ge=1, le=3)

class TaskRead(BaseModel):
    id: UUID
    title: str
    created_at: datetime
```

No default means required. A default makes a field optional to provide; it does not automatically mean the value may be `None`. `title: str | None` permits `None` but remains required unless it also has a default such as `= None`.

<TypeScriptComparison>

A TypeScript interface checks developer-authored code but disappears at runtime. A Pydantic model behaves more like a Zod schema plus inferred object: construction executes validation and returns a runtime object.

</TypeScriptComparison>

## Strictness and coercion

Pydantic commonly converts compatible inputs—for example, a UUID string into `UUID`. That is useful at transport boundaries, but surprising conversions should be controlled with strict types, field configuration, or `ConfigDict(strict=True)`. Decide whether your API accepts convenient coercion; do not discover the policy accidentally.

`extra="forbid"` rejects unknown input keys and catches client typos. Response models can use different policy because they are constructed from trusted application data.

## Reading validation errors

`ValidationError.errors()` returns structured entries containing a location, error type, message, and input context. Treat error types and locations as machine-usable; avoid building logic around English messages.

```python
from pydantic import ValidationError

try:
    TaskCreate.model_validate({"title": "", "project_id": "bad"})
except ValidationError as exc:
    for error in exc.errors():
        print(error["loc"], error["type"])
```

<CommonMistake>

`Optional[str]` means `str | None`; it does not mean the input key may be omitted. Requiredness and nullability are separate dimensions.

</CommonMistake>

<ProductionNote>

Reject unknown write fields unless compatibility requires otherwise. Silent extras hide client mistakes and can create mass-assignment vulnerabilities when payloads later feed persistence code.

</ProductionNote>

## Exercises

<Exercise id="pydantic-models-1">

Create `ProjectCreate` with required `name` of 1–80 characters and optional `description` that defaults to `None`.

<Solution>

```python
class ProjectCreate(BaseModel):
    name: str = Field(min_length=1, max_length=80)
    description: str | None = None
```

The description is both nullable and omittable.

</Solution>
</Exercise>

<Exercise id="pydantic-models-2">

Predict whether `priority: int = 2` accepts the input string `"3"`, then make the whole model strict.

<Solution>

Default Pydantic validation coerces a compatible numeric string. Add `model_config = ConfigDict(strict=True)` to require already-correct runtime types.

</Solution>
</Exercise>

<Exercise id="pydantic-models-3">

Reject a misspelled `projet_id` key instead of ignoring it.

<Solution>

Set `model_config = ConfigDict(extra="forbid")`. Validation then reports the extra key while also reporting the missing required `project_id`.

</Solution>
</Exercise>

<Checkpoint>

You can distinguish requiredness, nullability, defaults, constraints, coercion, and unknown-field policy.

</Checkpoint>

## Summary

`BaseModel` turns runtime input into a validated boundary object. Make field presence, `None`, defaults, coercion, and extra-key handling deliberate rather than relying on annotation appearance.
