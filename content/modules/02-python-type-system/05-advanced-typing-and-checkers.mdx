## Small tools with precise jobs

`Literal` restricts a value to enumerated constants. `Final` tells checkers a name should not be rebound. `ClassVar` marks class-level data so dataclasses and checkers do not treat it as an instance field.

```python
from typing import ClassVar, Final, Literal

DEFAULT_LIMIT: Final = 50
SortDirection = Literal["asc", "desc"]

class Task:
    table_name: ClassVar[str] = "tasks"
```

These are static constraints. `Final` does not make an object deeply immutable and `Literal` does not reject runtime input.

## Overloads describe correlated calls

Use `@overload` when return type depends on argument shape in a way a union cannot express. Overload signatures are for checkers; one implementation handles runtime calls.

```python
from typing import Literal, overload

@overload
def fetch_task(task_id: str, *, required: Literal[True]) -> Task: ...
@overload
def fetch_task(task_id: str, *, required: Literal[False] = False) -> Task | None: ...

def fetch_task(task_id: str, *, required: bool = False) -> Task | None:
    task = repository.find(task_id)
    if required and task is None:
        raise TaskNotFoundError(task_id)
    return task
```

Do not write overloads that claim more than the implementation guarantees. If the correlation is not valuable to callers, prefer the simple union.

## mypy and pyright

Both are mature static analyzers with different implementation and inference choices. Pyright powers Pylance and is fast; mypy is widely used and extensible. Pick one required checker in CI so developers share one verdict. Running both can be useful for libraries, but it increases policy cost.

Start strict for new application code: disallow untyped definitions, warn on unused ignores, check untyped bodies, and prevent implicit optional behavior. For a legacy codebase, tighten package by package and measure the remaining escape hatches.

```toml title="pyproject.toml"
[tool.mypy]
python_version = "3.13"
strict = true
warn_unreachable = true

[tool.pyright]
pythonVersion = "3.13"
typeCheckingMode = "strict"
```

<CommonMistake>

`# type: ignore` without an error code or explanation becomes permanent invisible debt. Narrow it to the specific diagnostic and link the library issue when a stub is wrong.

</CommonMistake>

<ProductionNote>

The highest-value checks live at boundaries: service inputs and outputs, repository protocols, configuration, and serialization. Perfect typing inside one-off glue is less valuable than preventing `Any` from crossing those boundaries.

</ProductionNote>

<Exercise id="types-tooling-2">

When is `Final[list[str]]` insufficient for immutability, and what is a better annotation?

<Solution>

`Final` prevents rebinding the list name but permits `append`. Use `Final[tuple[str, ...]]` when the collection contents should also be immutable.

</Solution>
</Exercise>

<Exercise id="types-tooling-3">

Your project contains 200 untyped files. Propose a safe strictness rollout.

<Solution>

Require strict checking for new packages, check bodies in existing typed functions, enable reports for untyped definitions, then migrate one dependency-oriented package at a time. Keep CI on one configured checker and track explicit, coded ignores.

</Solution>
</Exercise>

<Checkpoint>

You can identify whether a feature constrains a value, a binding, a class member, or a relationship between calls—and configure one checker as enforceable policy.

</Checkpoint>

## Summary

Advanced typing tools should make public contracts more truthful. Use overloads sparingly, remember static markers do not validate runtime data, and make checker strictness an incremental team policy.
