## Two systems, one program

Python remains dynamically typed when annotations are present. The interpreter usually stores annotations and executes the same objects; a checker such as mypy or pyright analyzes source without becoming the runtime. External data is still untrusted.

```python
def close_task(task_id: str) -> bool:
    return "not actually a bool"  # runs; a checker rejects it
```

<TypeScriptComparison>

Both TypeScript types and Python annotations can disappear from enforcement at runtime. Python differs because libraries inspect annotations at runtime and because untyped Python code can spread `Any`, which disables checking through an expression.

</TypeScriptComparison>

## Any, object, and unknown data

`Any` tells the checker to permit essentially every operation. It is an escape hatch, not Python's equivalent of TypeScript `unknown`. `object` accepts every Python value, but you must narrow it before using specific operations—making it the closer `unknown` analogue.

```python
def stringify(value: object) -> str:
    if isinstance(value, str):
        return value
    if isinstance(value, int):
        return str(value)
    raise TypeError(f"unsupported value: {type(value).__name__}")
```

Use `Any` at a boundary only when a library truly offers no contract, then validate or narrow immediately. Letting it flow through service code turns off the alarm system.

## None, unions, and narrowing

`None` is one singleton value and one type. Python has no `undefined`. A missing dictionary key, omitted function argument, and explicit `None` are different states that require explicit modeling when the distinction matters.

```python
def find_task(task_id: str) -> Task | None:
    ...

task = find_task("t-1")
if task is None:
    raise TaskNotFoundError("t-1")
reveal_type(task)  # Task to a checker
```

Narrow with `is None`, `isinstance`, membership checks, pattern matching, or a user-defined `TypeGuard`. Avoid truthiness when empty strings, zero, or empty collections are valid.

<CommonMistake>

`if value:` does not mean `value is not None`. It also rejects `0`, `False`, `""`, and empty containers.

</CommonMistake>

<ProductionNote>

Static types defend developer-controlled paths. Pydantic will later validate runtime request data. Use both; asking one to do the other's job creates either false confidence or excessive runtime modeling.

</ProductionNote>

## Exercises

<Exercise id="types-runtime-1">

Choose `Any` or `object` for a logging function that accepts any value but only calls `repr(value)`. Explain the choice.

<Solution>

Use `object`. Every value supports `repr`, and the checker will prevent accidental calls to arbitrary methods. `Any` would unnecessarily disable checking.

</Solution>
</Exercise>

<Exercise id="types-runtime-2">

Fix `return task.title if task else "missing"` when a valid task object might define false truthiness.

<Solution>

```python
return task.title if task is not None else "missing"
```

The condition now tests the modeled absent state precisely.

</Solution>
</Exercise>

<Exercise id="types-runtime-3">

Narrow `str | int` and reject negative integers while returning a normalized string ID.

<Solution>

```python
def normalize_id(value: str | int) -> str:
    if isinstance(value, int):
        if value < 0:
            raise ValueError("id must be non-negative")
        return str(value)
    return value.strip()
```

Each branch has a concrete type.

</Solution>
</Exercise>

<Checkpoint>

You can say which guarantees exist only in the checker, contain `Any`, and model absence without confusing it with falsiness.

</Checkpoint>

## Summary

Annotations improve design and tooling but do not validate runtime values. `object` preserves safety for unknown values; `Any` opts out. Model `None` explicitly and narrow unions with evidence.
