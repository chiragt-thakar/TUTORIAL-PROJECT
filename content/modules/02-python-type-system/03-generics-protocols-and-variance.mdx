## Preserve relationships with generics

A generic says several positions share a type relationship. `Any` erases that relationship.

```python
from typing import TypeVar

T = TypeVar("T")

def first(items: list[T]) -> T:
    if not items:
        raise ValueError("items cannot be empty")
    return items[0]
```

Given `list[Task]`, the result is `Task`. A bound limits valid types while preserving the concrete subtype:

```python
class Entity:
    id: str

E = TypeVar("E", bound=Entity)

def entity_id(entity: E) -> str:
    return entity.id
```

## Protocols express behavior

Protocols provide structural typing: a class satisfies a protocol by having compatible members, without inheritance or registration.

```python
from typing import Protocol, TypeVar

T_co = TypeVar("T_co", covariant=True)

class Reader(Protocol[T_co]):
    def get(self, entity_id: str) -> T_co: ...
    def list(self) -> list[T_co]: ...

class TaskWriter(Protocol):
    def add(self, task: Task) -> None: ...
```

Split reading and writing when useful. A service can require only its actual dependency. Structural contracts make an in-memory repository and future SQLAlchemy repository interchangeable without coupling either class to an interface base.

<TypeScriptComparison>

Python `Protocol` is the closest match to TypeScript's structural interfaces. Unlike a normal Python abstract base class, it does not require explicit inheritance. It still exists mainly for static analysis unless marked `@runtime_checkable`, whose runtime check is shallow.

</TypeScriptComparison>

## Variance in practice

Covariance means a producer of `SpecialTask` can stand in for a producer of `Task`; it only returns values. Contravariance means a consumer able to handle any `Task` can stand in for one asked to handle only `SpecialTask`. Mutable containers are invariant because they both produce and consume.

If `list[SpecialTask]` were accepted as `list[Task]`, the callee could append a plain `Task`, violating the caller's list. Prefer read-only abstractions such as `Sequence[Task]` when covariance is useful. Do not add variance declarations until the direction of data is clear.

<CommonMistake>

A repository protocol with twenty methods becomes a disguised concrete dependency. Define cohesive capabilities used by the consumer, and let architectural boundaries—not a generic framework—drive reuse.

</CommonMistake>

<ProductionNote>

Protocols make tests cheaper: service tests can use a small fake implementing the same behavior. They do not remove the need for integration tests proving the SQLAlchemy implementation honors the contract.

</ProductionNote>

## Exercises

<Exercise id="types-generics-1">

Write generic `last(items: Sequence[T]) -> T` and reject an empty sequence.

<Solution>

```python
from collections.abc import Sequence
from typing import TypeVar
T = TypeVar("T")

def last(items: Sequence[T]) -> T:
    if not items:
        raise ValueError("items cannot be empty")
    return items[-1]
```

</Solution>
</Exercise>

<Exercise id="types-generics-2">

Define the smallest protocol needed by a service that only retrieves a task by ID.

<Solution>

```python
from typing import Protocol

class TaskReader(Protocol):
    def get(self, task_id: str) -> Task: ...
```

Depending on this capability keeps unrelated repository operations out of the service contract.

</Solution>
</Exercise>

<Exercise id="types-generics-3">

Explain why `Sequence[SpecialTask]` can be accepted where `Sequence[Task]` is needed, while `list[SpecialTask]` cannot safely replace `list[Task]`.

<Solution>

The sequence interface only exposes values, so reading a subtype as its base is safe. A list permits writes; the receiver could insert a base `Task` into a list promised to contain only `SpecialTask`.

</Solution>
</Exercise>

</Checkpoint>

## Summary

Generics preserve type relationships. Protocols describe behavior structurally. Variance follows data direction: producers can be covariant, consumers contravariant, and mutable producer-consumers are normally invariant.
