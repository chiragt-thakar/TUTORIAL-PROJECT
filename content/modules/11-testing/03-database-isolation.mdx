## Test the database behavior you depend on

Repository tests should use the same database family as production when constraints, transactions, JSON, time zones, or locking matter. SQLite is useful but is not a drop-in PostgreSQL substitute.

One isolation strategy creates a transaction per test and rolls it back:

```python
@pytest.fixture
async def session(engine):
    async with engine.connect() as connection:
        transaction = await connection.begin()
        session = AsyncSession(bind=connection, expire_on_commit=False)
        yield session
        await session.close()
        await transaction.rollback()
```

If application code commits, use nested transactions/savepoints or truncate tables between tests. The fixture and application must share the exact connection for rollback isolation to work.

Test constraints, sorting, pagination boundaries, eager-loading behavior, and concurrent update rules—not SQLAlchemy itself.

## Common mistakes

Do not reuse state across tests, silently point tests at a developer database, apply migrations once months ago, or let parallel workers collide in the same schema.

## Production note

Build the test schema from migrations in CI. That proves the migration history, not only current metadata, can create a working database.

## Summary

Database tests earn their cost by verifying real constraints and transactions while rigorous isolation keeps every case independent.
