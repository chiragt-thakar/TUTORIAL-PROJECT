## One fast feedback loop

Ruff can format Python and enforce a broad set of lint rules quickly. Start from a small, intentional selection; enabling every rule creates contradictory policy and noisy migrations.

```toml title="pyproject.toml"
[tool.ruff]
target-version = "py313"
line-length = 100
src = ["src"]

[tool.ruff.lint]
select = ["E", "F", "I", "UP", "B", "SIM"]

[tool.ruff.format]
quote-style = "double"

[tool.mypy]
python_version = "3.13"
strict = true
```

Run formatting, linting, and types as separate checks so failures remain legible:

```bash
uv run ruff format --check .
uv run ruff check .
uv run mypy src tests
```

Formatting removes style debate. Linting finds suspicious syntax and maintainability issues. Static checking validates annotated relationships. Tests exercise behavior. None replaces the others.

## Pre-commit without surprise

Pre-commit hooks provide early feedback, but CI remains authoritative because local hooks can be skipped. Pin hook revisions, keep hooks fast, and ensure the same underlying commands run in CI.

```yaml title=".pre-commit-config.yaml"
repos:
  - repo: https://github.com/astral-sh/ruff-pre-commit
    rev: v0.12.0
    hooks:
      - id: ruff-check
        args: [--fix]
      - id: ruff-format
```

In a real repository, select a currently reviewed revision rather than copying this example indefinitely. Automatic fixes are appropriate locally; CI should generally check without modifying files.

<TypeScriptComparison>

Ruff overlaps ESLint plus Prettier; mypy or pyright occupies the `tsc --noEmit` role. Python splits these concerns across tools, so one documented command sequence matters.

</TypeScriptComparison>

<CommonMistake>

Do not use `exclude` or blanket `noqa` to make a red repository green. Exclusions should describe generated or vendored code; targeted ignores should state the exceptional rule.

</CommonMistake>

<ProductionNote>

Pin tool versions in the development lock. A formatter upgrade can rewrite the repository and a checker upgrade can alter accepted inference even when runtime dependencies did not change.

</ProductionNote>

## Exercises

<Exercise id="tooling-quality-1">

Order these checks for fast local feedback: tests, format check, lint, static types.

<Solution>

A practical order is format check, lint, static types, then tests. The cheapest mechanical failures appear first. CI can run independent jobs concurrently.

</Solution>
</Exercise>

<Exercise id="tooling-quality-2">

A migration file intentionally has a long SQL string. Choose a narrow policy exception.

<Solution>

Use a per-file ignore for the specific line-length rule on the migrations path, or a line-level code if only one occurrence exists. Do not disable line length globally.

</Solution>
</Exercise>

<Exercise id="tooling-quality-3">

Why should CI not rely only on pre-commit?

<Solution>

Hooks can be skipped, may not be installed, and run on a developer's machine. CI supplies the shared enforceable environment and verdict.

</Solution>
</Exercise>

<Checkpoint>

You can explain what each quality tool proves, run them independently, and scope exceptions without weakening unrelated code.

</Checkpoint>

## Summary

Use Ruff for formatting and linting, one configured type checker for contracts, pre-commit for convenience, and CI for enforcement. Keep policy explicit, pinned, and narrow.
